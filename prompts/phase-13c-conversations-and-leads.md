# Phase 13c — Conversations and Leads

## Goal
After this, the dashboard nav has 9 real sections instead of 8: a new "Conversations" page (`/dashboard/conversations`) lists every conversation the widget has ever persisted for the business, with a message count and whether it produced a lead, linking to a detail page (`/dashboard/conversations/[id]`) that shows the full message transcript plus the associated lead's details inline if one exists. The existing "Leads" page is restyled to match the shell (same card-row treatment 13b applied elsewhere) and gains a "View conversation" link per row. This is the first real read path into `messages`/`conversations` from the dashboard — `authenticated` has had `SELECT` on `messages` since Phase 11 specifically anticipating this, but no page has read it until now.

## Decisions and assumptions

1. **Message count per conversation uses PostgREST's embedded-relationship count** (`.select('*, messages(count)')` against `conversations`), not an N+1 per-row count query or a new Postgres function. Confirmed applicable because `messages.conversation_id` is a real FK (unlike this project's several app-enforced polymorphic references). **Implementer must verify this against the installed `@supabase/supabase-js` version's actual behavior before relying on it** (this project's standing discipline for third-party API specifics, per Phase 7/9's "inspect before assuming" pattern) — if the embedded-count shape doesn't work as expected, fall back to a per-conversation count query; data volume at this stage makes either approach fine.
2. **"Has a lead" indicator on the conversation list is computed in-memory, not via a second per-row query.** The list page already needs `listLeadsForBusiness()`-equivalent data for the Leads page elsewhere; here it fetches all of the business's leads once and builds a `Set<conversation_id>` (or `Map<conversation_id, Lead>` if the lead's `id` is needed for the link) client-side-of-the-server-component, avoiding N+1 queries at a data volume where a dedicated join isn't yet justified — consistent with 13a's Decision 4 ("no speculative optimization at a scale this product isn't at").
3. **New function `lib/messages.ts`'s `listMessagesForConversation(supabase, businessId, conversationId)`** returns full `Message[]` rows (not the narrowed `ConversationMessage` shape `listRecentMessages` returns), ascending chronological order, capped at 500 rows as a defensive bound (not a real limit at current usage — `askSalesEmployee()`'s own rate limits make a 500-message conversation implausible in v1, but an unbounded query is still avoided on principle, matching `lib/schemas/lead.ts`'s existing "bound everything, even when unlikely to matter yet" discipline).
4. **New function `lib/leads.ts`'s `getLeadForConversation(businessId, conversationId)`** — tenant- and conversation-scoped, `.maybeSingle()`, `null` if no lead exists for that conversation (the common case — most conversations have no lead, per Phase 10's "no contact info → no lead row" rule). Used by the conversation detail page.
5. **New function `lib/conversations.ts`'s `listConversationsForBusiness(supabase, businessId)`** returns conversations ordered `created_at` descending (most recent first), with the embedded message count (Decision 1) — no pagination in this prompt, same "don't optimize prematurely" reasoning as Decision 2; revisit if a business accumulates enough conversations for this to matter.
6. **Nav order: Conversations placed between Knowledge and Leads** — Overview, Business Profile, Products, Services, FAQs, Knowledge, Conversations, Leads, Widget Settings. Reflects the actual data flow (a conversation may or may not produce a lead), and keeps the two most closely related sections adjacent.
7. **Message content renders as plain text** (React's default JSX escaping, no `dangerouslySetInnerHTML`, no markdown interpretation) — consistent with `docs/security.md`'s "AI output is untrusted" principle and matching how the Phase 12 widget's own `message-bubble.tsx` already renders content. Both the prospect's and the AI's messages get this treatment identically; no special-casing by `role`.
8. **The Leads page restyle is presentational plus one new link** (`View conversation`, using the row's existing `conversation_id` field, which every lead has always had per the Phase 10 schema) — `status-select.tsx` and `actions.ts` are untouched, matching 13b's restyle-only discipline. `interest_id` continues to render as a raw UUID (unchanged from today) — resolving it to a human-readable product/service name would require new queries into `products`/`services` by ID, which is real scope beyond "restyle + link," not attempted here.
9. **Overview's Conversations `StatCard` href updates from `/dashboard/leads` to `/dashboard/conversations`** — the one-line fix the 13a code comment already flagged as pending.
10. **No new database migration.** `conversations`, `messages`, and `leads` all already have the RLS/grants this phase needs (`authenticated`: `SELECT` on all three) — confirmed in `STATE.md` §6 and the Phase 11 migration's own comment anticipating this read.
11. **Read-only.** No escalation/takeover action, no reply-from-dashboard, no conversation status field — none of these exist anywhere in the schema or `PRODUCT.md` today; that's Phase 15's job (Human handoff), not this one.
12. **`getLeadForConversation(businessId, conversationId)` does not take a `supabase` client parameter — it constructs one internally, matching `lib/leads.ts`'s own existing convention (`createLead()`, `listLeadsForBusiness()`, `updateLeadStatus()` all do the same), not `lib/conversations.ts`/`lib/messages.ts`'s client-injection pattern.** This is a deliberate choice, confirmed by re-inspecting all three existing `lib/leads.ts` functions (see "Existing code inspected"), not an inconsistency to silently carry forward. The two patterns exist for a real reason, not developer preference: `lib/conversations.ts`/`lib/messages.ts` need client injection because both are called from the Clerk-session dashboard path *and* the service-role widget path (Phase 11's `42501` bug was exactly this — a function missing the injection it needed for its actual multi-path callers). `lib/leads.ts` has no service-role caller today — lead capture is not wired from the widget (Phase 11 Decision 16, unchanged through 13a/13b) — so every existing function in that file, and this new one, only ever runs under a Clerk session. If lead capture is ever wired to the widget path in a later phase, `lib/leads.ts` would need the same client-injection retrofit Phase 11 applied to `lib/conversations.ts`/`lib/messages.ts` at that time — not preemptively here, since that would be speculative for a caller that doesn't exist yet.

## Security requirements
- `docs/security.md` §1/§3 (tenant isolation): every new function filters by `businessId` in addition to RLS, matching this codebase's universal defense-in-depth convention. `getConversationForBusiness()`'s existing `null`-on-cross-tenant contract is reused unchanged for the detail page's authorization gate.
- All reads use the Clerk-session client (`createServerSupabaseClient()`), never the service-role client — this phase introduces no new service-role usage.
- Message content (both prospect- and AI-authored) is rendered as plain text only, per `docs/security.md`'s "AI output is untrusted" principle — no `dangerouslySetInnerHTML`, no markdown rendering, no link auto-detection that could enable injection.
- No secret touched, no new env var.

## Error handling
- A cross-tenant or nonexistent conversation ID in the URL: `notFound()` → Next.js's standard 404, same as every existing `[id]/edit` page — no distinction between "doesn't exist" and "belongs to another business" (existing project-wide convention, `docs/security.md` §10).
- Any Supabase failure on the new list/get functions: existing `AppError`/`logAndGetUserMessage` convention, no raw error surfaced.
- Zero conversations / zero messages in a conversation (shouldn't happen given Phase 11's unconditional persistence, but not asserted against): the list page's existing empty-state pattern; the detail page shows an empty transcript state rather than crashing if it ever occurs.
