### Tighten businesses table grants — completed 2026-08-11
- What exists now: user manually verified Data API exposure after Phase 3 and found `anon`/`authenticated` both held full CRUD plus `TRUNCATE`/`REFERENCES`/`TRIGGER` on `businesses` — broader than Phase 3's Decision 4 intended. Diagnosis: Postgres `GRANT` is additive, so Phase 3's explicit `grant select ... to authenticated` never overrode a pre-existing database-level `ALTER DEFAULT PRIVILEGES` from this project's provisioning (predating Supabase's April-2026 auto-expose opt-out default). Data was not actually exposed to unauthorized reads — RLS (enabled + forced, one `SELECT` policy) already gated `SELECT`/`INSERT`/`UPDATE`/`DELETE` regardless of the broad grants — but `TRUNCATE` bypasses RLS entirely (not a row-scoped operation), so the excess `TRUNCATE` grant was a real gap, not cosmetic. Migration `supabase/migrations/20260811145006_tighten_businesses_grants.sql` revokes all privileges from `anon` and revokes `INSERT`/`UPDATE`/`DELETE`/`TRUNCATE`/`REFERENCES`/`TRIGGER` from `authenticated`, leaving only the existing `SELECT` grant. `docs/architecture.md`'s "Database" section gained a note: verify actual grants after any migration that creates a table, don't assume the migration's explicit `GRANT` is the only one in effect.
- Key files: `supabase/migrations/20260811145006_tighten_businesses_grants.sql`, `docs/architecture.md`.
- Migrations applied: **applied and verified by user 2026-08-11.** Confirmed: `authenticated` has `SELECT` only, `anon` has zero grants, `TRUNCATE` is denied for both, and cross-tenant isolation still holds correctly.
- Env vars added: none.
- Decisions made this phase: scoped to `businesses` only, not a database-wide `ALTER DEFAULT PRIVILEGES` fix for future tables (separate follow-up, see next entry); `service_role` left untouched (expected to bypass RLS/hold broad privileges by design) — see `prompts/tighten-businesses-table-grants.md`.

- **`GEMINI_API_KEY` naming correction (2026-08-12) — resolved, recorded for the record.** The Gemini API key's env var has always correctly been `GEMINI_API_KEY`. `lib/embeddings.ts` (Phase 7) and `lib/rag.ts` (Phase 8) were both written reading `process.env.GOOGLE_API_KEY`, and `.env.local`/`.env.example`/`docs/security.md`/`STATE.md` all documented `GOOGLE_API_KEY` to match — a naming mistake that went uncaught through two phases because everything was *internally* consistent (code, example file, and docs all agreed with each other, just on the wrong name) and no live Gemini call had been exercised yet to surface it as a missing-env-var failure. Compounding it: mid-Phase-8, `.env.example` briefly showed the correct `GEMINI_API_KEY` on one line while everything else still said `GOOGLE_API_KEY`; this agent treated `.env.example` as the stale outlier and "restored" it to match the wrong name, which was the opposite of the right fix. The user caught the actual mismatch directly, confirmed `GEMINI_API_KEY` is correct, and updated `.env.local` to it. **Fixed:** `lib/embeddings.ts:95`, `lib/rag.ts:73` (`process.env.GEMINI_API_KEY!`), `.env.example`, `docs/security.md` §5's env var table, and this file's §2/§5 entries all now read `GEMINI_API_KEY`. `docs/architecture.md` was checked and has no `*_API_KEY` references, so needed no change. Historical prompt files (`prompts/phase-7-embeddings-pgvector.md`, `prompts/phase-8-langchain-rag.md`) still say `GOOGLE_API_KEY` in prose — left as-is, since prompts are point-in-time implementation contracts, not living documentation; this bullet is the durable record of the correction.
- `npm run build` and `npx tsc --noEmit` pass cleanly as of Phase 1.
- `npm run lint` previously reported 15 errors / 304 warnings, all inside `.agents/` and `.claude/` skill-package files (not application code). Fixed 2026-08-11 under the trivial-change exemption: `eslint.config.mjs` now ignores `.agents/**` and `.claude/**` (they are skill packages, not app code, and were never intended to be linted as part of this project). `npm run lint` reports zero errors and zero warnings across the whole repo.
- **Function-level default-privileges: schema-wide fix abandoned, resolved via per-function discipline instead (closed 2026-08-12, see §1).** Three migrations were attempted for a schema-wide `REVOKE EXECUTE ... FROM anon, authenticated` on functions in `public`. First (`20260812191914_...`, revoke from `public`) assumed the gap was Postgres's ordinary `PUBLIC` default — wrong, live `has_function_privilege()` check still failed. Second (`20260812200105_...`, revoke from `anon, authenticated` explicitly) corrected which roles to name but still failed the same live check, because neither migration specified `FOR ROLE` and both only ever edited the `postgres`-owned default ACL entry — `pg_default_acl` revealed a *second*, separate entry owned by `supabase_admin` (the role Supabase's own tooling actually provisions objects under). Third (`20260812213356_...`, `alter default privileges for role supabase_admin ...`) correctly targeted that owning role, but **failed to apply**: `npx supabase db push` returned `permission denied to change default privileges` (`42501`) — the `postgres` role a migration connects as has no membership in `supabase_admin` on managed Supabase, and altering another role's default privileges requires that membership (or superuser). **This is a platform constraint, not a fixable bug — no normal-connection workaround exists, and it will not be retried.** All three migration files remain in `supabase/migrations/` as a record of the investigation; none are retroactive and `match_knowledge_chunks` was unaffected throughout (fixed individually via its own direct `revoke`). **Neutralized 2026-08-13:** the third migration's failure was permanent and was blocking every later `db push` (including Phase 10's) from getting past it, so its statement was removed in place (comments kept, per `prompts/neutralize-blocked-default-privileges-migration.md`) — it's now an intentional no-op, not a retroactive change to the live database. The first two migrations were left untouched. **Standing rule adopted instead, recorded in `docs/architecture.md`:** every new Postgres function must get its own explicit `revoke execute ... from anon` (or equivalent least-privilege grant) in its own migration, verified live via `has_function_privilege()` — the pattern already proven for `match_knowledge_chunks`. This must be checked per new function going forward; there is no schema-wide safety net for functions the way there is for tables. **Still flagged, not yet done:** the Phase 3 table-level default-privileges fix has never been independently re-checked against `pg_default_acl` for this same two-owning-roles issue.
