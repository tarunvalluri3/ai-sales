## 1. Current phase

**Phase 8 — LangChain RAG — implemented, pending user manual verification.**

Phases 6 and 7 are closed (see §2). The pending item that was blocking Phase 8 is now resolved (final outcome, not a retry candidate):

1. **Direct Phase 6 regression check — CONFIRMED COMPLETE by the user.** A plain product edit-and-save on a real test business (no knowledge-document angle) completed with no error; the generated knowledge document and its chunks regenerated correctly. See the Phase 6 §2 entry.
2. **Default privileges on functions — resolved as a documented platform constraint, mitigated by per-function discipline, not by a schema-wide fix.** Two prior migration attempts were each wrong in a different way, both caught only by the user's own live verification, not by inspection:
   - `20260812191914_...` (`revoke execute on functions from public;`) assumed the gap was Postgres's ordinary `PUBLIC` default. Wrong — `has_function_privilege()` on a throwaway function still showed `anon`/`authenticated` both `true` after it ran.
   - `20260812200105_...` (`revoke execute on functions from anon, authenticated;`) corrected which roles to name, but still failed the same live check. Root cause found via `pg_default_acl`: **two separate default ACL entries exist for functions in `public`** — one owned by `postgres` (already clean), one owned by `supabase_admin` (grants `anon`/`authenticated`/`postgres`/`service_role`) — and neither prior migration specified `FOR ROLE`, so both only ever edited the `postgres`-owned entry.
   - `20260812213356_default_privileges_revoke_execute_functions_supabase_admin.sql` (`alter default privileges for role supabase_admin in schema public revoke execute on functions from anon, authenticated;`) correctly targeted the actual owning role — but **failed to apply**: `npx supabase db push` returned `permission denied to change default privileges` (Postgres `42501`). On managed Supabase, the role a migration connects as (`postgres`) has no membership in `supabase_admin`, which Supabase reserves for its own internal provisioning tooling — altering another role's default privileges requires membership in it (or superuser), which a normal migration connection never has. **This is a platform constraint, not a fixable bug** — there is no normal-connection workaround, so this approach is abandoned rather than retried a fourth time.
   - **Standing rule adopted instead:** every new Postgres function this project creates gets its own explicit `revoke execute ... from anon` (or equivalent least-privilege grant) in its own migration, verified live via `has_function_privilege()` after creation — the same pattern already proven working for `match_knowledge_chunks`. `docs/architecture.md`'s function-default-privileges note has been corrected a third time to record this as the final conclusion.
   - **Still flagged, not decided or scheduled:** whether the Phase 3 table-level default-privileges fix has this same `supabase_admin`-vs-current-role gap has not been independently re-verified against `pg_default_acl` — Phase 5's throwaway-table check found zero default grants, consistent with the table case being fine, but predates this session's discovery of the two-owning-roles issue.

Phase 8's implementation prompt is being written this session, per the user's explicit go-ahead now that item 2 above is closed.

### Tighten businesses table grants — completed 2026-08-11
- What exists now: user manually verified Data API exposure after Phase 3 and found `anon`/`authenticated` both held full CRUD plus `TRUNCATE`/`REFERENCES`/`TRIGGER` on `businesses` — broader than Phase 3's Decision 4 intended. Diagnosis: Postgres `GRANT` is additive, so Phase 3's explicit `grant select ... to authenticated` never overrode a pre-existing database-level `ALTER DEFAULT PRIVILEGES` from this project's provisioning (predating Supabase's April-2026 auto-expose opt-out default). Data was not actually exposed to unauthorized reads — RLS (enabled + forced, one `SELECT` policy) already gated `SELECT`/`INSERT`/`UPDATE`/`DELETE` regardless of the broad grants — but `TRUNCATE` bypasses RLS entirely (not a row-scoped operation), so the excess `TRUNCATE` grant was a real gap, not cosmetic. Migration `supabase/migrations/20260811145006_tighten_businesses_grants.sql` revokes all privileges from `anon` and revokes `INSERT`/`UPDATE`/`DELETE`/`TRUNCATE`/`REFERENCES`/`TRIGGER` from `authenticated`, leaving only the existing `SELECT` grant. `docs/architecture.md`'s "Database" section gained a note: verify actual grants after any migration that creates a table, don't assume the migration's explicit `GRANT` is the only one in effect.
