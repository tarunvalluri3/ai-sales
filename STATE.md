2. **Default privileges on functions — resolved as a documented platform constraint, mitigated by per-function discipline, not by a schema-wide fix.** Two prior migration attempts were each wrong in a different way, both caught only by the user's own live verification, not by inspection:
   - `20260812191914_...` (`revoke execute on functions from public;`) assumed the gap was Postgres's ordinary `PUBLIC` default. Wrong — `has_function_privilege()` on a throwaway function still showed `anon`/`authenticated` both `true` after it ran.
   - `20260812200105_...` (`revoke execute on functions from anon, authenticated;`) corrected which roles to name, but still failed the same live check. Root cause found via `pg_default_acl`: **two separate default ACL entries exist for functions in `public`** — one owned by `postgres` (already clean), one owned by `supabase_admin` (grants `anon`/`authenticated`/`postgres`/`service_role`) — and neither prior migration specified `FOR ROLE`, so both only ever edited the `postgres`-owned entry.
   - `20260812213356_default_privileges_revoke_execute_functions_supabase_admin.sql` (`alter default privileges for role supabase_admin in schema public revoke execute on functions from anon, authenticated;`) correctly targeted the actual owning role — but **failed to apply**: `npx supabase db push` returned `permission denied to change default privileges` (Postgres `42501`). On managed Supabase, the role a migration connects as (`postgres`) has no membership in `supabase_admin`, which Supabase reserves for its own internal provisioning tooling — altering another role's default privileges requires membership in it (or superuser), which a normal migration connection never has. **This is a platform constraint, not a fixable bug** — there is no normal-connection workaround, so this approach is abandoned rather than retried a fourth time. **Neutralized 2026-08-13** (`prompts/neutralize-blocked-default-privileges-migration.md`): since this failure was permanent, the file was blocking every subsequent `db push` (including Phase 10's two pending migrations) from getting past it. The `alter default privileges` statement was removed from the file in place, leaving only its investigation comments plus a note explaining the removal — the file is now an intentional no-op. `20260812191914_...` and `20260812200105_...` were left untouched, per explicit instruction.
   - **Standing rule adopted instead:** every new Postgres function this project creates gets its own explicit `revoke execute ... from anon` (or equivalent least-privilege grant) in its own migration, verified live via `has_function_privilege()` after creation — the same pattern already proven working for `match_knowledge_chunks`. `docs/architecture.md`'s function-default-privileges note has been corrected a third time to record this as the final conclusion.
   - **Still flagged, not decided or scheduled:** whether the Phase 3 table-level default-privileges fix has this same `supabase_admin`-vs-current-role gap has not been independently re-verified against `pg_default_acl` — Phase 5's throwaway-table check found zero default grants, consistent with the table case being fine, but predates this session's discovery of the two-owning-roles issue.

### Tighten businesses table grants — completed 2026-08-11
- What exists now: user manually verified Data API exposure after Phase 3 and found `anon`/`authenticated` both held full CRUD plus `TRUNCATE`/`REFERENCES`/`TRIGGER` on `businesses` — broader than Phase 3's Decision 4 intended. Diagnosis: Postgres `GRANT` is additive, so Phase 3's explicit `grant select ... to authenticated` never overrode a pre-existing database-level `ALTER DEFAULT PRIVILEGES` from this project's provisioning (predating Supabase's April-2026 auto-expose opt-out default). - **Function-level default-privileges: schema-wide fix abandoned, resolved via per-function discipline instead (closed 2026-08-12, see §1).** Three migrations were attempted for a schema-wide `REVOKE EXECUTE ... FROM anon, authenticated` on functions in `public`. First (`20260812191914_...`, revoke from `public`) assumed the gap was Postgres's ordinary `PUBLIC` default — wrong, live `has_function_privilege()` check still failed. Second (`20260812200105_...`, revoke from `anon, authenticated` explicitly) corrected which roles to name but still failed the same live check, because neither migration specified `FOR ROLE` and both only ever edited the `postgres`-owned default ACL entry — `pg_default_acl` revealed a *second*, separate entry owned by `supabase_admin` (the role Supabase's own tooling actually provisions objects under). Third (`20260812213356_...`, `alter default privileges for role supabase_admin ...`) correctly targeted that owning role, but **failed to apply**: `npx supabase db push` returned `permission denied to change default privileges` (`42501`) — the `postgres` role a migration connects as has no membership in `supabase_admin` on managed Supabase, and altering another role's default privileges requires that membership (or superuser). **This is a platform constraint, not a fixable bug — no normal-connection workaround exists, and it will not be retried.** All three migration files remain in `supabase/migrations/` as a record of the investigation; none are retroactive and `match_knowledge_chunks` was unaffected throughout (fixed individually via its own direct `revoke`). **Neutralized 2026-08-13:** the third migration's failure was permanent and was blocking every later `db push` (including Phase 10's) from getting past it, so its statement was removed in place (comments kept, per `prompts/neutralize-blocked-default-privileges-migration.md`) — it's now an intentional no-op, not a retroactive change to the live database. The first two migrations were left untouched. **Standing rule adopted instead, recorded in `docs/architecture.md`:** every new Postgres function must get its own explicit `revoke execute ... from anon` (or equivalent least-privilege grant) in its own migration, verified live via `has_function_privilege()` — the pattern already proven for `match_knowledge_chunks`. This must be checked per new function going forward; there is no schema-wide safety net for functions the way there is for tables. **Still flagged, not yet done:** the Phase 3 table-level default-privileges fix has never been independently re-checked against `pg_default_acl` for this same two-owning-roles issue.
